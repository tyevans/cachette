# ADR-0107: The Python reference is generated from the compiled module, and its prose lives in the Rust doc comment

## Context

Cachette is a world simulation engine. The core is Rust. The control plane is
Python.[^1] A developer who builds a game on this engine writes Python and
never opens the core. A product record states that need: the developer must be
able to learn the control plane without reading its source.[^2]

The Python package holds a small amount of pure Python and re-exports a
compiled extension module. A separate crate holds the interpreter binding,
because the core crate holds none.[^3] A build tool compiles that crate into the
extension module. The binding library copies a Rust doc comment onto the Python
object that it creates, so a Rust doc comment becomes a Python docstring at run
time.

**The prose that the developer wants is written in Rust.** The bindings crate
carries it. It answers what a call returns, in what unit a value is expressed,
and which error the call raises. Every error the engine raises is a declared
type, and the reader must be able to name it without reading a Rust file.[^4]

**A second declaration site for that prose already exists.** The package ships
a hand-written type stub beside the compiled module.[^5] A type checker reads
the stub. The stub declares the signature of every public member. It carries
prose for a few members, and it carries none for the methods a caller uses.

**A documentation tool reaches a compiled module in one of two ways.** It parses
source text, or it imports the module and reads the objects that the import
creates. A compiled module has no Python source text, so a parse reaches the
stub and never the module. An import reaches the module.

**A research report measured both paths against this repository.**[^6] A site
built by an import of the compiled module carried the prose of every method. The
same site built with module inspection turned off fell back to the stub and
carried no method prose at all. The build reported no error either way. The
report holds the sizes and every version number, because a record must not hold
material that a measurement or a release can change.[^7]

**The report also found that no candidate tool escapes the import.** Each of the
four tools it examined imports a compiled module in order to document it. The
import is therefore a property of the artefact and not a property of any tool.
It is a constraint on the documentation job, and a comparison of tools does not
show it.

**A stale copy of prose does not fail.** This project has recorded the shape:
one value declared in two places, both read as authoritative, with nothing that
fails when the copies disagree.[^8] The stub and the compiled module are two such
sites today, and they have already parted. Nine exception docstrings agree word
for word. One class docstring in the stub is an abridged copy of the Rust one,
and the paragraph it drops is the paragraph that warns against one value in two
places.[^9]

**A false claim about the stub already reached the tree.** The stub states in
its own docstring that a build regenerates it and that a job fails when the
result differs. No generator and no such job exists.[^10] A contributor who read
that sentence would conclude that a check protects the second site. Nothing
does.

## Decision

### D1. The published Python reference is generated by an import of the compiled extension module

The documentation build imports the compiled module and reads the docstrings
that the import creates. It does not derive the reference from source text.

This is the only path that reaches the prose. A reference derived from text
carries signatures and nothing else, and it looks like a working reference.

### D2. The prose of a member the compiled module provides lives in the Rust doc comment, and nowhere else

A class, a method, a property, a function or an exception that the compiled
module provides carries its prose in the Rust doc comment of the crate that
declares it. That crate is the bindings crate, and it is the one authoritative
site.[^3]

A contributor who changes what the reference says about such a member changes
the Rust doc comment. A contributor who adds prose for such a member adds a Rust
doc comment.

### D3. The type stub declares types, and carries prose only for a declaration the compiled module does not provide

The stub exists for the type checker. It states signatures.

Some declarations in the stub have no counterpart in the compiled module. A
typed dictionary that describes the shape of a returned mapping is one. Such a
declaration has no other home, so it carries its own prose and that prose is
authoritative.

Every other member of the stub carries no prose. A docstring on a member that
the compiled module provides is a copy, and this record forbids it.

### D4. The documentation job builds the extension before it builds the site, and it fails when the import fails

The job compiles the crate, installs the built module, and then runs the site
build. A configuration that turns module inspection off is forbidden by D1, and
the job must not depend on a reader who notices a smaller page.

The job therefore fails, rather than publishes, when the import does not happen.
A documentation build is a compile step. It is not a text step.

## Alternatives rejected

**Move the prose into the type stub, and generate the reference from text.**
This is the option that makes the import unnecessary. It also makes the stub a
second home for the whole of the bindings crate's prose, with nothing that fails
when the two copies disagree. The project has recorded that shape as a
defect.[^8] The trade becomes reasonable only when a check compares the two
sites, and no such check exists.

**Generate the stub from the compiled module.** This removes the second
declaration site rather than doubles it, and it is the right answer for the
signatures. It does not change this record, because the prose still comes from
the Rust doc comment. It is work, and a backlog item holds it.[^11]

**Bind the builder instead of the provenance.** A record that names one
documentation builder decides the cheapest thing in the choice. Every candidate
imports the module, the site configuration is a portable format that more than
one builder reads, and the report measured the swap as near free.[^6] The scope
rule asks whether a different choice costs more than a change made later. For
the builder it does not, so the builder is not a constraint and this record does
not hold it.[^7]

## Consequences

**The documentation job needs the Rust toolchain, and it costs what a wheel job
costs.** A job that installs a documentation tool and points it at the source
tree publishes an empty reference. A project that wants a fast documentation job
caches the build or accepts the cost.

**The builder stays replaceable, and the project uses Zensical today.** The
report tested that tool against this repository's own compiled module, and the
prose reached the page.[^6] The tool is young, and this record does not depend on
it. The site configuration is a portable format, a second builder reads the same
file, and the four decisions above hold whichever builder runs. A change of
builder is not a change to this record.

**A member with no Rust doc comment publishes with no prose, and nothing
fails.** This record fixes where the prose lives. It does not make anything write
the prose. The gap is now visible in one place instead of two, and that is the
whole of what it buys.

**The generated page repeats the project heading style.** The Rust doc comments
follow the documentation rule, so each carries its own references heading and
many carry an errors heading.[^12] A page that holds many members holds those
headings many times, and the page contents list shows the repetition. The report
measured it. It is a consequence of the rule that meets a generated page, and it
is not a defect in any tool. The project either chooses a heading level for a
docstring section or accepts the repetition.

**The stub is narrower than it was, and the prose it already holds is a defect
this record names and does not fix.** Nine exception docstrings and one class
docstring copy prose that the Rust source owns. A backlog item holds the removal
and the check that keeps it removed.[^11]

**The project cannot document its compiled surface with a static text tool.** A
tool that refuses to import a module cannot serve this reference. That closes
one family of candidates for as long as the prose lives in Rust.

**A reader of the reference reads prose that a contributor to the core wrote.**
The audience of a doc comment is now two audiences: the Rust reader, and the
Python developer the product record names.[^2] A doc comment written for the
first one alone under-serves the second, and no check can see that.
