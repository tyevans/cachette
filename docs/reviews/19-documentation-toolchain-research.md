# Working Report — Research Report 19, the Documentation Toolchain

This is the working report for research report 19. It states what the author
verified against a primary source, what the author could not verify, the
recommendation, and the single fact most likely to change the decision. The
research report itself holds the evidence and the version numbers.[^1]

Date of the work: 3 September 2026.

## 1. What the author verified against a primary source

**By reading this repository.**

- The repository has no documentation build. Three workflows exist, and none of
  them builds or publishes a site.[^2]
- The project manifest declares no documentation dependency in any dependency
  group.[^3]
- No site configuration file of any kind exists in the tree.
- One type stub exists, and it sits beside the compiled module.[^4]
- The stub holds 398 lines, 67 class or function definitions, and 36
  docstrings. Every docstring sits on a typed dictionary or on an exception
  class. No method of `World` and no method of `Camera` carries one.[^4]
- The Python bindings crate holds 1,558 lines, and 543 of them are doc comment
  lines.[^5]
- The author imported the built module and read four docstrings from it. PyO3
  puts the Rust doc comments on the Python objects.
- The stub's own docstring claims that the contributing guide requires a
  continuous integration check, that the build regenerates the stub, and that a
  job fails on a difference. No generator and no such job exists, and the
  contributing guide says something else.[^4] [^6] The findings register now
  holds this.[^7]

**By reading Zensical's own sources.**

- The publisher, the MIT licence, the repository language split and the
  repository creation date, read through the GitHub API.
- Release 0.0.58, published 2 September 2026, and 58 releases in total.
- The package classifier `Development Status :: 3 - Alpha`, the Python floor of
  3.10, and the eight runtime dependencies, read from the package index.
- The roadmap statement that Zensical is alpha software, and the list of
  features that are not built, which includes API documentation and versioning.
- Native reading of `mkdocs.yml`, the reversible migration path, and the named
  unsupported settings, which include `hooks`.
- mkdocstrings support since release 0.0.11, the two named limitations, and the
  open cross-reference issue.
- Footnote support and its configuration, the Python Markdown extension list,
  the search plugin, and the transitional fork of `mike` for versioning.
- The documented GitHub Pages workflow, which uses the standard Pages actions
  and not a Zensical action.

**By building a site.**

The author built a real site against this repository's compiled module with
Zensical 0.0.58 and `mkdocstrings-python` 2.0.8 on CPython 3.13.5. Three
configurations were built. The measured page sizes, build times, footnote
counts and heading counts are in section 4 of the research report.[^1]

## 2. What the author could not verify, and why

- **That the Zensical rewrite passes every mkdocstrings handler option
  through.** The author confirmed that one option, `allow_inspection`, changes
  the output. The author did not read the Zensical source for the rest.
- **The documented GitHub Pages workflow.** The author did not run it. There is
  no Pages setup in this repository to run it against.
- **A comparison build with Material for MkDocs.** The author did not build the
  same site with the other builder, so the comparison in the report is reasoned
  and not measured.
- **Sphinx and pdoc against the compiled module.** The author did not test
  either. The claim that both import the module comes from their documented
  design, not from a run.
- **Whether MyST can accept this repository's footnote syntax.** The author did
  not test it. The report marks the claim as unverified.
- **The whole repository documentation set.** The probe built one page against
  one class. It did not build 361 Markdown documents, so the report states no
  build time for a full site.

## 3. The recommendation, in one paragraph

Adopt Zensical as the builder, but write the decision record about the
constraints rather than about the tool. The load-bearing question came out in
Zensical's favour and the author measured it: Zensical builds this project's
PyO3 module reference today, with the Rust doc comments, the navigation, the
search and the footnotes all intact. Zensical is alpha software by its own
statement, but it reads `mkdocs.yml`, so Material for MkDocs runs against the
identical configuration file and the choice is reversible at near zero cost.
The two things worth binding in a record are that the published reference is
generated by importing the compiled extension module, and that the docstring
lives in the Rust doc comment and never in the type stub. Sphinx is rejected
because this repository's whole corpus is Markdown with Python Markdown
footnote syntax and would need conversion. pdoc is rejected because it
documents an API and nothing else, and this repository's documentation is
mostly prose.

## 4. The single fact most likely to change the decision

**Where the docstring lives, not which tool renders it.**

The author built the same page twice. With module inspection allowed, the page
was 105,348 bytes and held every method's prose. With inspection turned off,
the tool fell back to the type stub, the page fell to 29,038 bytes, and every
method's prose disappeared.

If the project ever decides that the docstring belongs in the stub, the whole
comparison changes. The documentation job would stop needing the Rust
toolchain, static tools would become viable, and Sphinx would become a serious
candidate on source text alone. The author judges that the wrong trade, because
it creates a second declaration site for 543 lines of prose with nothing that
fails when the two copies disagree. A project that adds such a check may
reasonably decide otherwise.
