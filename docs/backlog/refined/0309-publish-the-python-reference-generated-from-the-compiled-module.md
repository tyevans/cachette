## Why

**A developer who builds a game on this engine cannot learn the Python package
without reading its source, and the reference is the largest part of the
answer.** A product record states the need and names the audience.[^1] A reader
who wants to know what a call returns, in what unit a value is expressed, or
which error a call raises, opens a Rust file today.

**The reference is generated, not written.** A record binds it: the published
Python reference comes from an import of the compiled extension module, and the
job that builds it fails when the import fails.[^2] This item builds that job.

**The repository has no documentation build of any kind.** There is no site
configuration, no documentation dependency and no publishing job. A research
report looked and reported it.[^3]

**A build that reaches the wrong source succeeds and reports nothing.** The same
report measured it against this repository. A site built by an import of the
compiled module carried the prose of every method. The same site built with
module inspection turned off fell back to the type stub and carried no method
prose at all. Neither build reported an error.[^3] That is why D4 exists, and it
is the reason this item is a compile job rather than a text job.

## Impact review

**Governed by.** ADR-0107 D1 and D4.[^2]

**D1, the reference is generated by an import of the compiled module.** The
reference quadrant of the site holds one directive that names the compiled
module. It holds no written interface prose. The build never sets the option
that turns module inspection off, and the configuration states that in a comment
beside the setting it does not use.

**D4, the job builds the extension before the site and fails when the import
fails.** The job compiles the bindings crate, installs the built module into the
build environment, then builds the site. It fails rather than publishes when the
import does not happen. A reader must not be the thing that notices a smaller
page.

**D2 and D3 govern this item without changing it.** This item writes no prose
for a member that the compiled module provides, and it writes nothing into the
type stub.[^2] The gap in the Rust doc comments is real and a separate item
repairs it.[^4] This item publishes the gap rather than filling it, which is
what the record says the arrangement buys.

**Changes.** No record changes.

**Creates.** No record. One open choice in the decisions register asks whether
the site configuration stays in a portable format, and it recommends that it
does.[^5] A second open choice asks how a published page cites a repository
document that a reader cannot open, and this item is the first to meet it.[^6]

**Blockers.** One governs this item. Nobody in the tree can say where the site
publishes, or who turns the publishing on.[^7] Express the site address as a
parameter of the job and cite the blocker. Do not invent an address. Two
further blockers govern the prose rather than the build: one holds every cost
figure, and one asks whether an upgrade changes hands when the ground does.[^8]
[^9] No page this item publishes states a figure or answers that question, so
neither stops the work.

**Precedent.** Item 0307 must close first. The Python package declares its
public interface in two places and nothing compares them, so a reference built
over both publishes whichever site the tool reached.[^10] The priority index
states the same order and gives the same reason.[^11] Two findings this plan
recorded show what a published claim costs when nothing checks it.[^12] [^13]

## What the work does

Add the site configuration, the reference page and the publishing job.

- Add the documentation dependencies to a dependency group of their own. They
  are build tools, not runtime dependencies of the package.
- Write the site configuration in the portable format, per the open choice and
  its recommendation.[^5] State the navigation with the four Diátaxis
  quadrants, and leave the three prose quadrants empty for the items that fill
  them.[^14]
- Write the reference page as one directive over the compiled module, with a
  member filter that removes the members the import collects and a reader does
  not want. The research report measured which ones appear.[^3]
- Add the job. It builds the extension, installs it, builds the site, and
  publishes the output to the address the blocker holds.
- **Prove that the job fails when the import fails.** Turn module inspection off
  behind a temporary change, run the job, and confirm that it fails. A guard
  that has never been shown to fire has not been shown to exist.[^15]

## What it does not do

It does not write a tutorial, a how-to guide or an explanation page. Three
separate items hold those.

It does not write or repair any Rust doc comment. One item holds that.[^4]

It does not touch the type stub. Item 0307 holds that, and it runs first.[^10]

It does not choose the builder. The record refuses to bind one, and a change of
builder is not a change to the record.[^2]

## What it costs

**The job costs what the wheel job costs, and the record accepts that.** The
build compiles the bindings crate, so it needs the Rust toolchain.[^2] A project
that wants a fast documentation job caches the build or accepts the cost.

Nothing at run time changes. No simulation code changes.

## Done when

- The job builds the extension, installs it, and builds the site, in that order.
- The published reference holds the prose of every method that carries a Rust
  doc comment. A reader finds a sentence on the page that exists only in the
  bindings crate.
- The job fails when the import of the compiled module fails, and somebody has
  seen it fail.
- No page in the repository holds hand-written prose for a member the compiled
  module provides.
- The site address is a parameter of the job, and the job cites the blocker
  rather than a value.
- The whole check command runs green.
