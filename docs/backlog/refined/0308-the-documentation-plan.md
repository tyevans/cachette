## Why

**A developer who builds a game on this engine writes Python, and cannot learn
the Python package without reading the source.** A product record states that
need and names the audience: one game developer who has never opened this
repository.[^1] The package explains itself only in places that reader does not
reach. A docstring arrives after the import works. The orientation document
holds one worked example and nothing runs it. The prose for a method sits in a
Rust file.

This item is the plan. It states the structure of the documentation, the order
of the work, and what checks it. The items numbered above it do the work.

**The plan uses Diátaxis.** That framework splits documentation into four kinds
by what the reader is doing: a tutorial for learning by doing, a how-to guide
for reaching one goal, reference for looking a thing up, and explanation for
understanding why.[^2] The four are not interchangeable. A page that mixes two
serves neither reader.

**One record already binds the largest of the four.** The published Python
reference is generated by an import of the compiled extension module. The prose
of a member that module provides lives in the Rust doc comment. The type stub
carries prose only for a declaration the module does not provide. The
documentation job builds the extension before it builds the site, and it fails
when the import fails.[^3] The plan honours all four, and the impact review
below takes them one at a time.

## Impact review

**Governed by.** ADR-0107 D1, D2, D3 and D4.[^3]

**D1, the reference is generated by an import.** The plan does not write a
reference page. It plans a build. One item creates the site and the job that
builds it, and the reference quadrant of that site holds a directive that names
the compiled module and no prose.[^4] The plan therefore never asks anybody to
write a page of interface prose, and no item below produces one.

**D2, the prose lives in the Rust doc comment.** The plan names the prose gap as
work in the bindings crate, not as work in a documentation directory. A separate
item reads the generated page, finds each member with no prose or with prose
written for a Rust reader alone, and repairs the Rust doc comment.[^5] The record
says in its own consequences that no check can see this gap, so the item is a
reading task with a stated finish line.

**D3, the stub declares types and carries prose only where the module provides
none.** The plan writes nothing into the type stub and moves no prose into it.
Item 0307 holds the generator, the two checks and the removal of the eleven
copied docstrings.[^6] This plan does not repeat that work. It orders itself
behind it, for the reason the priority index already gives: a reference built
over two declaration sites publishes whichever site the tool reached.[^7]

**D4, the job builds the extension first and fails when the import fails.** The
site item owns the job. The job compiles the crate, installs the built module,
and then builds the site. It never sets the option that turns module inspection
off. It fails rather than publishes when the import does not happen, because a
build that falls back to the type stub succeeds and publishes a smaller page.

**Changes.** No record changes. The plan needs no amendment to ADR-0107, and it
asks for none.

**Creates.** No decision record. One open choice goes to the decisions register
with options and a recommendation, because a published page cannot follow a
repository path and the plan must not invent the answer.[^8]

**Blockers.** One is open and this plan opens it. Nobody in the tree can say
where the site publishes or who turns the publishing on, and that is missing
information rather than a judgement.[^9] Every item below states the site
address as a parameter and never as a value. Two further blockers govern the
prose. One holds every cost figure, so no page states a performance number
without citing it.[^10] One asks whether an upgrade changes hands when the
ground does, so no page answers that question.[^11]

**Precedent.** Three findings shape the plan. A statement that nothing executes
and nothing derives costs the reader's trust the first time it is wrong, and the
product record measures that cost on this project twice.[^1] A generated page
changes when the code changes, and a hand-maintained list does not.[^12] The
project has published two false claims in the document a newcomer reads first,
and this work recorded both.[^13] [^14]

## The structure

### The reference quadrant is a build, and it comes first

The reference holds every public name of the package. Twelve names come from the
compiled module: the `World` class, the `Camera` class, the `version` function
and nine exception types.[^15] The typed dictionaries that describe a returned
mapping live in the type stub, because the module does not provide them, and
they carry their own prose there.[^3]

**It comes first for three reasons, and none of them is the symmetry of the
framework.**

The first is that it is the only quadrant that cannot decay quietly. It is
derived from the artefact, so it changes when the artefact changes. Every other
quadrant is prose, and prose states a false thing without failing.

The second is that it answers the sharpest cost the product record names. A
developer today opens a Rust file to learn what a call returns and which error
it raises.[^1] Nothing else in this plan closes that.

The third is that the other three quadrants cite it. A tutorial that names a
method needs somewhere to send the reader. Prose written before the reference
exists invents its link targets.

**What must exist in the Rust source before the reference is usable.** Every
public member needs a doc comment. That comment must say what the call returns,
in what unit a value is expressed, and which error the call raises. It must read
for a Python developer and not only for a contributor to the core.[^3] The
generated page shows which members have nothing. Repairing them is one item, and
it is work in the bindings crate.

### The tutorial is one page, and it is the smallest run that ends in a result

**The smallest tutorial takes a reader from nothing to a running world in one
sitting.** It names each thing the reader must already have. It installs the
package. It builds a world, spawns a set of units, gives one order over that
set, steps the world, and reads the tick, the state hash and one column of the
event log. It ends with the reader holding a number that came out of a
simulation they built.

That is the worked example the orientation document already holds, and nothing
runs it.[^16] The tutorial is that example, executed by the test suite, with the
prose a first reader needs around it.

**What the tutorial deliberately does not cover.** It does not open a window. It
does not explain the pyramid, the selector, the fixed-point scale or the
threading model. It does not tune anything. It states no performance figure. It
does not mention the agent server. It does not explain why any part of the
engine is the way it is. A reader who asks why is reading the wrong quadrant,
and the tutorial says so once at the end.

### The how-to guides name four goals

Each guide names a goal a reader arrives with, and each maps onto a call that
exists on the surface today.

1. **Install the package and build the extension.** The reader has a machine and
   no environment. This guide names the interpreter floor, the Rust toolchain,
   the package manager and the command runner. It ends with an import that
   works.
2. **Repeat a run exactly.** The reader wants two runs to agree. This guide names
   the seed, the thread count, the state hash and the event log, and it states
   what the guarantee covers. Both other audiences of the product directory
   arrive with this goal as well.
3. **Read what one tick did, without walking the population.** The reader wants
   the result of a step. This guide reads the event columns and the gather
   columns into arrays, and it works on the arrays.
4. **Order a set of units with one command.** The reader wants many units to do
   one thing. This guide builds the set, sends one command, and says plainly
   that a loop is the thing the engine exists to make unnecessary.

**A fifth goal exists and the plan holds it back.** Drawing a frame through the
camera is a real goal, and `Camera` is a public name that the reference must
cover.[^15] A guide for it waits until the four above publish, because a reader
who cannot install the package cannot draw anything.

### The explanation quadrant is small, and it mostly links out

**This repository already holds the explanation.** Decision records state why
each constraint exists. Research reports hold the evidence. Registers hold what
the project believed and corrected. Copying any of it into a documentation site
creates a second declaration site for a fact whose original lives elsewhere,
with nothing that fails when the copies disagree. That is the defect shape this
project names first in its own rule.[^12]

The explanation quadrant therefore holds only what has no other home. Three
pages qualify. Each is a translation for an audience the records do not address,
and not a copy of a record.

1. **The rule that governs every program on this engine.** Python builds a
   selector and sends one command, and Python does not walk a population. The
   product record requires the documentation to state this, and to state plainly
   whether anything enforces it.[^1] Nothing does, and the package docstring
   already says so.[^15] A record states the rule for a contributor to this
   project. No document states it for the reader who will break it.
2. **What determinism gives the reader, and what it does not.** Two runs agree.
   That is not a statement that either run is right, and the project has recorded
   a defect that was deterministic and passed every determinism test.[^17] A
   reader who builds an experiment on the guarantee needs both halves.
3. **Which surface a program may depend on, and what is missing.** The package
   holds a compiled module, a demonstration window and a tool server that serves
   this repository. The product record requires the reader to tell them apart,
   and to learn what the package cannot do yet rather than conclude that they
   failed to find it.[^1] The two findings this work recorded are instances of
   that gap.[^13] [^14]

Every other explanation is a footnote that names a record. The pages state a
conclusion and cite the source, which is what the documentation rule asks of any
document in this tree.[^18]

### Where it publishes, and what runs the build

The site is one static site built from this repository. The build is a compile
step: it builds the extension, installs it, then builds the site.[^3] A
continuous integration job runs it and publishes the output.

**The address and the publishing switch are not in the tree, and this plan does
not invent them.** A blocker holds them, and every item states the address as a
parameter.[^9]

**The builder is not a constraint.** The record refuses to bind one, and the
research report measured the swap as near free, because the site configuration
is a portable format that a second builder reads.[^19] One open choice asks
whether the project keeps that format, and it recommends keeping it.[^20]

### What checks it, and by what

A documentation site that nothing verifies decays exactly like a stale record.
Four things check this one, and each fails rather than reports.

- **The build fails when the import fails.** This is D4. It stops the site
  publishing a reference that holds signatures and no prose.[^3]
- **Every example a reader can copy is executed.** One harness runs the code of
  every page and of the orientation document, and it fails when a snippet stops
  working.[^1] The orientation example runs today and nothing runs it, so this
  check starts by covering a snippet that already exists.
- **The list of public names is derived from the package.** A check reads the
  exported names from the installed package, compares them against the published
  site, and fails when the two disagree.[^1] This is the check that stops a name
  being added and never documented.
- **The stub and the module agree.** Item 0307 holds this, and it runs before any
  of the above.[^6]

## The order, and why

1. **0307**, the type stub generator and its two checks. It is not part of this
   plan and it must close first.[^6]
2. **0309**, the site, the reference build and the publishing job.
3. **0310**, the Rust doc comments that the reference publishes.
4. **0311**, the harness that executes every example.
5. **0312**, the tutorial.
6. **0313**, the how-to guides.
7. **0314**, the explanation pages.
8. **0315**, the check that derives the public name list from the package.

**The order answers to the reader, not to the framework.** The reference comes
first because it is generated, because it answers the question the product
record calls the sharpest, and because the prose quadrants cite it. The doc
comments come second because the reference publishes empty prose until they
exist, and because the generated page is what makes each gap visible. The
harness comes before the tutorial because the tutorial is the first executable
example, and a tutorial written before the harness is a tutorial nobody ever
runs. The explanation comes last because it is the smallest, and because reading
the three earlier quadrants decides how much of it is needed at all. The name
check comes last because it compares against a published site, and that site
must exist first.

## Done when

- Items 0309 to 0315 are complete.
- A reader who has never seen the package installs it and runs one tick from the
  published site alone, without opening this repository.
- Every public name of the package appears on the site, and a check derives that
  list from the package and fails when the two disagree.
- Every example on the site and in the orientation document is executed by
  something that fails when it stops working.
- The documentation job fails when the import of the compiled module fails.
- No page holds prose for a member the compiled module provides. That prose is
  in the Rust doc comment.
- The whole check command runs green.
